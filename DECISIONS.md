# Decisions Log

Design decisions made during the build, with rationale. For per-record data
decisions (dropped rows, corrected values), see the `decision_log` DB table.

## Production Hardening — git init + .gitignore

First git history for this project (all M1-M10 work existed only as
uncommitted files on disk until now). Inspected the full repository for
secrets, API keys, database files, raw datasets, generated outputs, and
caches before writing `.gitignore` — see the summary given to the user
for exactly what was excluded. Two judgment calls worth recording:

- **`data/raw/denture_base/denture_base_sellersprite.xlsx` is tracked,
  not ignored**, despite being a "raw dataset". It's small (~54KB), has
  no secrets/PII (public Amazon listing data), and is the one input the
  entire pipeline derives from — gitignoring it would make a fresh clone
  of this repo non-functional without externally re-supplying it. The
  standard "always gitignore data/raw/" convention exists for large or
  sensitive datasets; this one is neither.
- **`data/samples/gold_labels_pilot.xlsx` and `data/validated/denture_base/gold_labels.csv`
  are tracked, not ignored**, even though the latter is technically
  "generated" by `scripts/build_gold_dataset.py`. The pilot file contains
  human/model-under-explicit-instruction labeling judgment that cannot
  be regenerated by re-running any script — losing it from version
  control would mean redoing that judgment work from scratch. The gold
  CSV is small, hardcoded as a path dependency in several tests, and is
  meant to be a *frozen* benchmark by design (Milestone 4) — tracking it
  directly avoids requiring a fresh clone to run the build script before
  tests can pass.
- **Everything else data-shaped is ignored**: `database/*.duckdb` (7MB
  binary, 100% derived, regenerate via the pipeline scripts in
  PROGRESS.md's order), `data/interim/`, `data/processed/`,
  `data/exports/`, and `data/samples/*.csv` (the profiling report — pure
  pipeline byproduct, no judgment baked in, unlike the pilot xlsx in the
  same directory).

## Post-Milestone-10 — Human Review Workflow + Evaluation Report

- **Calibration is applied uniformly to rules and AI results, not just
  AI.** The previous binary `AI_CONFIDENCE_THRESHOLD` constant only ever
  gated AI output; rule-based results always bypassed it entirely. The
  new `_tier_for_confidence` is checked for both, reading
  `config/thresholds.yaml` dynamically rather than a hardcoded constant —
  consistent with the categories.yaml/thresholds.yaml pattern already
  used elsewhere (Milestones 6, 9).
- **The calibration tool is designed to say "I can't calibrate this yet"
  out loud.** `recommend_tiers` returns explicit `warnings` for a
  bimodal/sparse distribution or an unreachable precision target, rather
  than silently picking a threshold anyway. This surfaced a real,
  reportable finding (the classifier's confidence values are currently
  bimodal — 0.95 or 0.0, nothing between) instead of hiding it behind a
  plausible-looking `sampling_threshold` number.
- **`sample_for_qa` keeps the model's stated answer; `needs_review`
  doesn't.** A deliberate distinction: mid-confidence predictions are
  probably right and still useful downstream (flagged for audit, not
  discarded); low-confidence predictions are forced to `UNCERTAIN`
  because they're not trusted at all. Conflating the two tiers would
  have made the whole point of a 3-tier system moot.
- **The evaluation report never uses the brief's example numbers as
  targets.** Every section either reports a real measured number or says
  "not measurable yet" with the specific reason — see Review Extraction
  in `dashboard/pages/6_Evaluation_Report.py`, which reports 0 real
  insights honestly rather than a fabricated accuracy figure.

## Milestone 10 — Dashboard

- **Project-wide gotcha, now hit twice: pandas turns SQL `NULL` into
  float `NaN`, and `NaN` is truthy.** First caught in
  `scripts/detect_opportunities.py` (Milestone 9), now again in the
  dashboard's `if row.get(x):` patterns. Any code that runs a DuckDB
  query through `.df()` and then checks a value with plain truthiness or
  `is not None` is suspect — use `pd.notna()`. Documented prominently in
  `docs/dashboard_spec.md` and in `data.py` itself since this is clearly
  a recurring trap for this codebase, not a one-off mistake.
- **Numbered page filenames (`1_Category_Overview.py`, etc.), not the
  original unnumbered stub names.** Streamlit sorts sidebar pages
  alphabetically by filename; without numbers, "Data Quality Center"
  would sort before "Listing Explorer" and "Market Map", breaking the
  intended page order. The original empty stubs (`category_overview.py`
  etc.) were deleted rather than left alongside the numbered ones, to
  avoid Streamlit showing duplicate blank pages.
- **Dashboard is strictly read-only** (`duckdb.connect(..., read_only=True)`).
  It never writes, including to caches that could be mistaken for
  persisted state — every number is a live query.
- **The dashboard was verified in a real browser, not just written and
  assumed correct.** All 3 bugs in Milestone 10's PROGRESS.md entry were
  found this way; none would have been caught by the existing unit-test
  suite, since the pipeline's own tests don't exercise pandas
  DataFrame-to-Streamlit-widget rendering at all.

## Milestone 9 — Opportunity Engine

- **No single score.** Every signal is 3 named, independently-inspectable
  conditions, never collapsed into one number — that collapse is exactly
  the "AI says this is a winning product" pattern the milestone said not
  to build.
- **Tri-state status (`signal_present`/`signal_absent`/`insufficient_data`)**,
  not a boolean. Given how sparse real demand/review data is right now,
  a boolean would have silently reported ~all of today's real results as
  false negatives instead of "we don't have enough data yet."
- **Bug: pandas `.df()` turns SQL `NULL` into `NaN`.** `float('nan') is
  None` is `False`, so every missing-data check in `signals.py` silently
  passed. Caught by comparing the real pipeline's output before/after
  switching to `fetchall()` (22/11 split vs. the correct 33/0 split).
  Full writeup in `docs/opportunity_signals.md`. Lesson: any DB read
  feeding an `is None` check must not go through pandas conversion, or
  must explicitly convert `NaN` back to `None` first.
- **Proxies are labeled in the data, not just in docs.** The
  accessory-activity condition's stored `description` field says "weak
  proxy, not real attach-rate data" on every row — a deliberate choice so
  the caveat travels with the data itself, not only with documentation
  someone might not read.

## Policy — "manual review" includes the labelling model work done under explicit user instruction

Milestone 4 ("Building your gold dataset") states ground truth should come
from manual human review, not from asking the labelling model to generate the answers.
Flagged this directly: the 50 labels in `data/validated/denture_base/gold_labels.csv`
were produced by the labelling model, at the user's explicit, item-by-item direction
(e.g. "manually inspect each of the 50 products... enter YES/NO/UNCERTAIN").

User's ruling: **the labelling model work done under explicit user instruction counts
as manual review for this project.** `reviewer = model` stays as-is and
is accepted as satisfying the "manually reviewed" requirement — it does
not need to be redone by a human. This does not retroactively change
anything about how `needs_review` rows are handled (those still need a
closer look per `docs/entity_resolution.md`/`docs/classification_guidelines.md`);
it resolves the reviewer-provenance question, not the confidence question.

## Milestone 7 — Market Engine

- **Finally populated `categories` and backfilled `listings.category_id`**
  — a gap explicitly flagged and left open since Milestone 3
  ("`category_id` is left NULL in this milestone. No category-resolution
  logic exists yet"). Category-level market metrics are meaningless
  without knowing which category a listing/product belongs to, and we
  already know it (every listing ingested so far came from the
  `denture_base` pilot export) — inserting the one category row and
  backfilling is resolving a known gap with information already in hand,
  not inventing a new hardcoded assumption.
- **Only `relevance_class = 'RELEVANT'` listings feed the market engine.**
  `UNCERTAIN` and `IRRELEVANT` listings are excluded entirely — including
  them would put the exact category contamination Milestones 2 and 5
  exist to remove back into every downstream number. This is why the
  pilot's real totals are small (12 of 105 listings) — that's the
  population correctly scoped, not a bug.
- **`None` for missing data, never `0`**, on every metric. Given real
  sales/revenue coverage in this pilot is ~2/12 and ~1/12 respectively,
  defaulting missing values to 0 would have silently misrepresented
  nearly every product's numbers as "confirmed zero sales" instead of
  "no data yet" — coverage counters travel with every product's metrics
  specifically so this is checkable, not just asserted.
- **`product_listings.is_best_listing` is finally written.** The column
  existed in the schema since the very first milestone but nothing ever
  populated it until the market engine determined an actual best-selling
  listing per product.

## Milestone 6 — Product Entity Resolution

- **Schema change to `product_listings`**: `reviewed BOOLEAN` → `review_status VARCHAR`.
  The original schema (dictated verbatim by the user in an earlier step)
  had `reviewed`; Milestone 6 explicitly requires `review_status` as one
  of the 5 required output fields, and it matches the pattern already
  used by `listing_classification`. Table was empty, so this was a
  straight `DROP`/recreate, not a destructive migration.
- **New `match_candidates` table** (the candidate-pair table Milestone 6
  asks for) is a full audit trail — every pair that survived blocking,
  including NO_MATCH and UNCERTAIN, not just confirmed matches.
  `product_listings` holds only the final resolved state.
- **Both `match_candidates` and `product_listings` are regenerated from
  scratch each run** (`DELETE` then re-`INSERT`), not upserted. Both are
  fully derived from the current listings + matching logic; a listing's
  `product_id` can legitimately change between runs as new matches are
  found, so upserting by a stale key would leave orphaned rows behind.
- **Stage 4 (technical attribute similarity) scoped to price**, not
  package weight/dimensions. Those fields exist in the raw SellerSprite
  export but were never brought into the normalized `listings` schema
  (a known gap since `docs/data_dictionary.md`). Price-only scoring was
  validated against all 5 manually-verified pairs before deciding this
  was sufficient for this milestone — extending to weight/dimensions is
  a natural follow-up, not a currently-blocking gap.
- **Every listing gets a `product_id`**, including ones matched to no
  one else (a stable singleton, derived from the listing's own
  `listing_id`). This was a deliberate choice so `product_listings` is a
  complete mapping ready for later market-capacity rollups, not just a
  sparse table of the pairs that happened to match.

### Bug: non-deterministic candidate blocking

`title_fingerprint`'s tie-breaking among equal-length words depended on
Python's `set` iteration order, which is hash-randomized per process —
re-running the identical pipeline against identical data produced a
different candidate-pair count each time (88, then 87, then 91 across
three consecutive runs before the fix). Root cause: `sorted(set(words),
key=len, reverse=True)` has no secondary key, so ties fall back to
whatever order the set happens to iterate in that process. Fixed with a
deterministic secondary key (`key=lambda w: (-len(w), w)`), verified
identical output across `PYTHONHASHSEED=0,1,2`, and pinned with a
regression test. Caught during this milestone's own verification pass,
before being reported as a final result — see PROGRESS.md for detail.

## Milestone 3 — Normalization

- **`listing_id` = sha1(marketplace|asin)**, not a random UUID. Same ASIN
  always yields the same `listing_id`, so re-ingestion is idempotent
  (`ON CONFLICT ... DO UPDATE` rather than ever inserting duplicates).
- **Duplicate ASIN resolution (open question #3 from data_dictionary.md):**
  when the same ASIN appears twice in a raw export, the first occurrence is
  kept and the rest are dropped, logged to `decision_log` as
  `duplicate_asin_dropped` with the full dropped row preserved in
  `old_value`. Applies to `B0FMK8XB26` in the current pilot file.
- **Rows with a missing ASIN are dropped**, logged as `row_excluded`. ASIN
  is the only reliable identifier in this schema; a listing without one
  cannot be deduplicated or referenced downstream.
- **Out-of-range/invalid values are nulled, not the whole row.** A negative
  price or an out-of-[0,5] rating nulls just that field and logs a
  `normalization_rejected_value` decision with the original raw value
  preserved — the row itself is kept.
- **`review_count` is always NULL** for this source — SellerSprite's export
  has no review-count column (see data_dictionary.md §12). Not invented or
  imputed.
- **`category_id` is left NULL** in this milestone. No category-resolution
  logic exists yet; assigning a hardcoded category id here would violate
  PRINCIPLES.md principle 9 (no hardcoded category assumptions).
- **Parquet export uses `data/processed/`**, not `data/interim/` — treated
  as "fully normalized, deterministic, ready to use" output, distinct from
  the AI-classification/purification stage that will land in
  `data/validated/`.

### Incident: normalization pipeline briefly overwrote the raw source file

While building `export_listings_parquet`, an early version ran:

```sql
COPY (SELECT * FROM listings WHERE raw_source_file = ?) TO ? (FORMAT PARQUET)
```

with `[raw_source_file, out_path]` as bound parameters. DuckDB bound these
**out of order** for this statement shape (parameterized WHERE clause +
parameterized COPY destination in one statement) — the WHERE-clause value
(`data/raw/denture_base/denture_base_sellersprite.xlsx`, a relative path)
was used as the **destination**, resolving against the working directory
and silently overwriting the actual raw `.xlsx` file with Parquet bytes.

Caught immediately (the very next ingest run failed to re-read the file as
Excel). Recovered from an untouched copy in the user's Downloads folder;
sha256 verified to match the hash pinned in `docs/data_dictionary.md`
before and after restoration — no data was lost.

Fix: `export_listings_parquet` now never binds the COPY destination (or any
value used inside the same COPY statement) as a `?` parameter — both the
destination path and the WHERE-clause filter value are inlined as
quote-escaped literals instead. It also hard-refuses to write to any path
containing `data/raw` as a defense-in-depth guard. A regression test
(`tests/integration/test_ingest_pipeline.py::test_raw_file_untouched_by_full_pipeline_run`)
runs the real pipeline end-to-end and asserts the raw file's hash is
unchanged.

### Confirmed SellerSprite field definitions (recorded only — no calculation change)

The user confirmed the following field definitions against SellerSprite's
own API documentation. This section records them for future reference.
**No market-calculation code changes as a result of this entry** — these
are documentation-only, pending a separate decision about whether/how to
use them.

- **上架时间** = the listing's availability/listing date. SellerSprite's
  ASIN-detail API calls this field `availableDate`; its separate market
  API tracks first/latest listing dates independently.
- **子体销量** = child-ASIN (variation) unit sales, as distinct from
  `parentUnitSales` (父体销量) in SellerSprite's sales-trend API.
- **子体销售额** = child-ASIN (variation) sales revenue, likewise distinct
  from parent-level revenue.

**Caveat (important):** SellerSprite does not always have genuine
child-ASIN sales data. Per their community guidance, when Amazon exposes
real variation-level sales, SellerSprite reports those; otherwise it may
substitute an *estimated* parent-level figure into the child-level field.
This means a value in this project's `子体销量` column is not guaranteed to
be an actual child-level observation — it could be a parent-level
estimate. Before this field is used in any market calculation, we must
first verify how the specific `denture_base_sellersprite.xlsx` export
represents unavailable child-level data (e.g. null vs. a copied parent
value) — that verification has not yet been done.

### M12 — Product Master Completion

**The gap:** `products` was defined in the schema since Milestone 4 but
`scripts/resolve_products.py` never wrote to it — 0 rows, always. The
dashboard had no choice but to reconstruct "the product" ad hoc on every
page load, by reading the best listing's title/image/brand and, separately,
`listing_classification.product_type` straight off that same best listing —
a third, *different* derivation of "the product's type" already existed in
`market/aggregation.py::_product_type_for_group` (mode across all the
product's listings) purely to build a category-level histogram, and was
discarded rather than stored. Three inconsistent notions of "this product"
existed depending which code path you asked.

**Fix:** `matching/resolution.py::build_products()` now derives one
`products` row per resolved product_id (all 92, not just the 12
RELEVANT/market-scoped ones — the Product Master must cover every
resolved product for the Listing Explorer's full-traceability page too).
Wired into `scripts/resolve_products.py` right after `product_listings` is
written, via a new `replace_products()` repository function (same
delete-and-regenerate-from-scratch pattern as `match_candidates` and
`product_listings`).

Field-derivation judgment calls (deterministic, no LLM):
- `product_name`: the title of the product's best-selling listing
  (`market/sales.py::best_selling_listing`, PRINCIPLES.md's own definition —
  reused rather than re-implemented). Falls back to the
  lowest-listing_id listing's title when no listing in the group has any
  sales data, so naming is never silently arbitrary/input-order-dependent.
- `brand`: the mode brand across the product's listings; ties broken
  alphabetically (not dict/insertion order) for the same determinism
  reason as `title_fingerprint` (M6) and `product_type_discovery` (M11).
- `product_type`: mode of non-null `listing_classification.product_type`
  across the product's listings, or `None` if none are classified yet —
  which is every product today, since M11's classifier hasn't been built.
  Never invented.
- `confidence` (product identity confidence): the *weakest-link*
  match_confidence — the lowest confidence among the MATCH decisions that
  connected this product's listings. A singleton was never matched to
  anything, so it gets `None`, not a fabricated 1.0.
- `model`: `None` — no model-number extraction exists in this pipeline yet.

The dashboard (`dashboard/components/data.py::load_product_metrics`,
`load_product_ai_confidence`) now joins/reads `products` directly instead
of re-deriving these fields from listings on every load; `3_Product_Detail.py`
and `2_Market_Map.py` needed no changes since the returned column names
(`best_listing_title`, `best_listing_image_url`, `brand`, `product_type`,
`identity_confidence`) were kept stable — only their source changed, from
"whatever the best listing happens to have" to the stored Product Master
value. `dashboard/pages/4_Listing_Explorer.py::load_all_products` was left
untouched: its `sample_title`/`sample_brand` are explicitly labeled as an
audit-page sample (a `MIN()` across all a product's listings, including
IRRELEVANT ones), not a claim of "the" product identity — a different,
already-honest use case, not the bug this milestone fixed.

Regression tests: `tests/unit/test_resolution.py` (build_products'
naming/brand/confidence/type derivation rules in isolation) and
`tests/integration/test_resolution_pipeline.py::test_every_resolved_product_id_has_a_products_row`
(guards against the table silently going empty again) /
`test_products_have_a_name_and_no_invented_type`.

### M11 — Taxonomy v1 frozen

The user reviewed `docs/product_taxonomy.md` (the 3 auto-discovered
candidates from `product_type_discovery.py`) and approved all three,
renamed, with explicit reasoning for each judgment call:

- **CAND_01 → `DB_WAX_PLATE` / "Denture Base Wax Plate"** (9 listings, 8
  products). Approved as one type, not split by pack size (a pack-size
  difference should not create a new product type) and not split into
  the latent bite-wax/casting-wax sub-pattern discovery surfaced —
  rejected as premature at this sample size (4 vs. 4 listings), not
  because the pattern is imaginary.
- **CAND_02 → `DB_RELINE` / "Denture Reline Material/Kit"** (2 listings,
  2 products). Approved. Explicitly rejected the algorithm's
  auto-suggested label ("Adjustment Curing") as a tie-break artifact
  among equally-scored words, not a real judgment — "Reline" is the
  actual shared functional purpose (a different customer use case from
  fabrication material), and both titles support it directly.
- **CAND_03 → `DB_RESIN` / "Denture Base Resin"** (1 listing, singleton).
  Approved as its own type despite n=1. Explicit user reasoning: "A
  category with one product can still be a valid taxonomy class. The
  taxonomy should represent the market, not the current sample size."
  "Other" is reserved for genuinely unidentifiable product purpose, not
  for small samples of an identifiable one.

Structural decisions for v1, all explicit user calls:
- **Flat, no hierarchy.** A subtype split (e.g. `DB_RESIN` into Heat
  Cure/Self Cure/Flexible) was explicitly deferred — not enough data to
  justify it yet.
- **No "Other" bucket** for any of the three approved types.
- **No automatic expansion.** New listings appearing in future ingests
  must never silently add, split, or rename entries in a frozen taxonomy
  file. Any structural change requires a new versioned file
  (`denture_base_v2.yaml`) and a fresh discovery → review → approval
  cycle — the same reasoning as never editing a shipped API/schema
  version in place.

Recorded as: `config/taxonomy/denture_base_v1.yaml` (machine-readable,
`status: frozen`) and `docs/taxonomy_denture_base_v1.md` (the approval
record and rationale, mapping each frozen type back to its discovery
candidate). Neither file is consumed by any code yet — no classifier
exists, and no listing or product has been assigned any of these ids.
That is the explicit next step (M11 Stage 2), not part of this freeze.

### M11 Stage 2 — Product-type classifier built and evaluated

Built `src/dmie/classification/product_type_classifier.py` against the
frozen `denture_base_v1` taxonomy, without modifying the taxonomy, the
entity-resolution/product-identity code, or the `products`/
`product_listings` schema.

**Keyword signals live in a new, separate config
(`config/product_type_signals.yaml`), not in the taxonomy file.** The
taxonomy (`config/taxonomy/denture_base_v1.yaml`) only defines ids/names/
definitions — it was never meant to also carry classifier implementation
details, and conflating the two would mean any rules-layer tuning
requires touching a file explicitly documented as frozen. Revising a
keyword list changes how confidently the rules layer recognizes a match;
it does not change what the taxonomy means, so it doesn't need a new
taxonomy version.

**Rules layer is a keyword-scoring vote, not an if/elif chain.**
`apply_rules(title, signals)` takes the signal map as a parameter and has
no knowledge of `DB_RESIN`/`DB_WAX_PLATE`/`DB_RELINE` as Python literals —
tested directly by feeding it a fabricated taxonomy and confirming it
returns the fabricated id. A title scores every id by its keyword hits;
exactly one id scoring is a confident match, and — critically — more than
one id scoring is treated as a real, informative ambiguity (never
silently broken by picking the highest scorer), because vocabulary
genuinely overlaps: "acrylic" appears in both `DB_RESIN` (fabrication
material) and `DB_RELINE` (repair-kit material, same chemistry, different
purpose) titles. This exact overlap is what happens on `B0FMK8XB26` — see
PROGRESS.md's M11 Stage 2 entry for the full worked example. This is the
same "don't force 100% agreement by overfitting rules" philosophy already
established for relevance classification (`rules.py`'s own documented
"known limitation").

**New `product_type` section in `config/thresholds.yaml`** (not a
modification to any file the user said not to touch): rules 0.95, AI
automatic-accept 0.85, AI sampling floor 0.60. Below the floor, or with no
AI answer, `product_type` is forced to the literal string `"UNCERTAIN"` —
between the floor and automatic-accept, the AI's stated type is kept but
flagged `needs_review` (the tri-state pattern already used for relevance
and entity resolution: distinguish "no" from "don't know," never collapse
uncertainty into a fabricated 0/guess). These are the user's own example
numbers from the M11 Stage 2 instructions, not yet empirically calibrated
against a real AI-scored dataset (no `ANTHROPIC_API_KEY` is configured in
this environment) — same caveat `relevance.sampling_threshold` already
carries.

**An AI answer outside the frozen taxonomy is hard-rejected to
`UNCERTAIN`**, regardless of stated confidence — including the literal
string `"Other"`, which the taxonomy freeze explicitly banned. This is a
code-level guard, not just a prompt instruction, so a model that ignores
the prompt still can't corrupt the taxonomy.

**Evaluated on the 12 confirmed-relevant listings only, not the full 92
products** — 11/12 correct (91.7%), the one miss being the genuine
acrylic/reline ambiguity above, correctly deferred rather than guessed.
Extended to 2 more hand-reviewed listings from the relevance gold set for
a wider `DB_RESIN` check (12/14, 85.7%, same single ambiguity pattern, no
new failure modes) — see PROGRESS.md for the full comparison tables and
`tests/test_product_type_classifier.py` for the source of both.

**Not wired into any script or the live database.** No
`scripts/classify_product_types.py` was created and
`listing_classification.product_type` was not touched for any real row —
per explicit instruction not to classify all 92 products until this
evaluation has been reviewed. `build_products()` (M12) was confirmed via
test to consume classifier output correctly (mode-vote across a product's
listings, `None` — never a guess — for the one unresolved listing) without
any change to it or to the product-master schema.

### M11 Stage 3 — Product Master type integration

**New table (`listing_product_type_classification`) instead of reusing
`listing_classification`'s `confidence`/`reason`/`review_status`
columns.** Those columns already have an established meaning — the
relevance decision's own confidence/reason/status — and
`src/dmie/classification/evaluation.py` plus the whole relevance-review
pipeline read them expecting exactly that meaning. Writing product-type
classification's confidence/reason/review_status into the same row would
have silently overwritten the relevance decision's own values on every
re-run of the type classifier: a real instance of the "silently change
business definitions" failure the project principles explicitly forbid,
not a hypothetical. A dedicated table costs one more `CREATE TABLE` and
avoids the collision entirely, matching the existing pattern of one table
per classification/decision stage (`match_candidates`, `review_insights`,
`opportunity_signals`).

**`products` gets 2 new columns, not a repurposed existing one.**
`product_type_confidence`/`product_type_conflict` are new, distinct from
`products.confidence` (product IDENTITY confidence, from entity
resolution — the weakest-link match_confidence, M12). Reusing
`confidence` for a second, unrelated meaning would be the exact same
"silently change business definitions" mistake as above, just one level
up (product rather than listing). Applied to the live DB via a one-time
`ALTER TABLE ... ADD COLUMN` (the project has no migration tooling yet —
that's M14's job — so this was a manual, documented, idempotent
(`ADD COLUMN IF NOT EXISTS`) step; a fresh `init_project.py` run against a
new DB gets these columns for free since `schema.sql` now defines them).

**`product_type_confidence` = mean of the *winning* side's classification
confidences, not a plain vote-share fraction and not an average of all
listings' confidences.** A vote-share number (e.g. "2 of 3 listings
agree") would have been simpler to compute but throws away the actual
classifier-reported confidence values already sitting right there in
`listing_product_type_classification`. Averaging only the winning side's
confidences means a dissenting listing's (possibly low) confidence can't
dilute the reported number for the type that actually won — and a
dissenting listing is separately and explicitly surfaced via
`product_type_conflict`, so nothing about the disagreement is hidden,
it's just not blended into the confidence number.

**`product_type_conflict` is `True` on ANY disagreement, not just a
close vote.** A product with 9 listings agreeing and 1 dissenting is still
flagged — the point is to surface every genuine disagreement for human
attention (PRINCIPLES.md "human-in-the-loop" for ambiguous cases), not to
hide minority dissent behind a majority that happens to look confident.

**Real run against the live DB, not left as only unit-tested.** Per the
M11 Stage 3 brief's explicit "Verify: before NULL / after populated"
requirement, `scripts/classify_product_types.py` (new) and
`scripts/resolve_products.py` (re-run) were both executed for real against
the actual project database — not just demonstrated in tests — since a
"before/after" claim about the live DB has to be checked against the live
DB. Result: `products.product_type` non-null count went from 0 to 10 (of
11 market-scoped products); 0 conflicts flagged (expected — see
PROGRESS.md, most products at this pilot's scale have only 1-2 listings).

### M13 — AI Reliability Layer

**One shared `call_ai()` (`src/dmie/ai/client.py`), not 4 independent
try/except blocks bolted onto each existing function.** All 4 AI call
sites had identical structure (env check, SDK import check, call, index
`response.content[0].text`, brace-slice, `json.loads`) and identical
gaps (none of that had any exception handling). Fixing each site
independently would have meant writing and testing the same retry/parse/
logging logic 4 times, with 4 chances to drift out of sync later. One
shared function fixes all 4 at once and is the only thing that needs
testing directly against failure scenarios — the 4 call sites just need
one test each proving they degrade gracefully when it fails, which is a
much smaller surface.

**Retries cover both exceptions AND unparseable responses, under one
`max_retries` knob — not separate retry budgets.** An API-level failure
(timeout, rate limit, connection error) and a response with no valid JSON
in it are both "this attempt didn't produce usable data," and both are
plausibly worth retrying (a fresh model sample might parse fine; a
transient network blip might clear). Splitting them into separate retry
counters would be more configurable but is complexity nothing in this
project has asked for yet (PRINCIPLES.md principle 12) — one counter, one
loop, covering both failure classes, was the smaller and equally correct
design.

**Failure classification doesn't use the Anthropic SDK's own exception
hierarchy.** The `anthropic` package isn't installed in this environment
(confirmed: `ModuleNotFoundError`), the same reason every existing
`classify_with_ai`-style function already guards its import with
`try/except ImportError`. Importing `anthropic.APIError`/
`anthropic.RateLimitError`/etc. at module load time to catch them
specifically would make `dmie.ai.client` itself fail to import without
the package present, which is worse than the problem being solved — every
caller already tolerates the package being absent. `call_ai()` instead
catches a broad `Exception` at the API-call boundary and logs the
concrete exception type/message for diagnosis; anything that isn't its
own `ValueError` (raised internally for a response that didn't parse) is
bucketed as a generic API failure. This is coarser than distinguishing
"rate limited" from "timed out" from "connection refused," but none of
the current pipeline scripts need to react differently to those cases —
they all mean the same thing to a caller: this one AI call didn't work,
degrade to `UNCERTAIN`/`None` and move on.

**Business logic was not touched, and this was verified by re-running the
real pipeline, not just by re-running the test suite.** Re-ran
`scripts/classify.py` end-to-end against the live DB after the refactor:
output is byte-for-byte identical to the pre-M13 run (12/65/28,
77 auto_accepted/28 needs_review) — proof the refactor changed only
failure-handling mechanics, not any classification outcome.

### M14 — Run Versioning and Data Provenance

**Only the run history is append-only/versioned — the DATA tables
themselves still regenerate in place, unchanged from every prior
milestone.** The brief's stated problem was "pipeline scripts replace
tables on reruns" with no trace of what a previous run produced. Read
literally and maximally, "prevent silent overwriting" could mean turning
every DATA table (`products`, `listing_classification`,
`match_candidates`, `product_market_metrics`, ...) into a full historical
log — keeping every row from every run side by side, forever. That would
be a genuinely different data model (slowly-changing dimensions, or
event-sourcing) requiring changes to every repository write function,
every downstream query (the dashboard, `evaluation.py`,
`build_products()`), and a decision about how "current state" queries
would even work once a table can hold multiple generations of the same
row. That's exactly the kind of architecture redesign the project
principles say not to do without a documented, specific need beyond what
was asked — and the brief's own concrete requirements (`run_id`,
timestamp, version, "historical outputs must be traceable", "document how
to compare two runs") are all fully satisfiable by a permanent *run log*
sitting alongside the existing regenerate-in-place tables, without
touching how any of them are written. That's the boundary drawn here,
and it's the one documented explicitly in `docs/pipeline_runs.md` rather
than silently under-delivered.

**`pipeline_version` reuses each stage's own existing version constant**
(`CLASSIFIER_VERSION`, `MATCHING_VERSION`) instead of inventing a new,
separate versioning concept. These constants already exist specifically
to answer "what code produced this row" (they're already stored in
`listing_classification.classifier_version`,
`listing_product_type_classification.classifier_method`'s sibling
version tracking, etc.) — introducing a second, parallel version number
for the same purpose would be exactly the kind of silently-diverging
duplicate concept the project has been careful to avoid elsewhere (e.g.
M12's product-type consolidation).

**`classification_runs` covers both relevance AND product-type
classification via a `stage` column, rather than 2 separate tables.**
The brief named `classification_runs` (singular) and
`product_resolution_runs` — 2 tables, but 3 scripts exist that need run
tracking (`classify.py`, `classify_product_types.py`,
`resolve_products.py`). Both classification scripts produce the same
shape of comparable counts (`total_classified`, `class_counts`,
`auto_accepted_count`, `needs_review_count`) — a `stage` discriminator
column is the natural fit, avoiding a 4th table for what's structurally
the same kind of run.

**`compare_runs()` excludes `run_id`/`created_at` from its reported
differences.** Every pair of runs will trivially differ on these two
fields — surfacing them as "differences" would bury the actual business
signal (did the counts change?) under noise that's true of literally
every comparison. Verified directly:
`test_compare_runs_surfaces_real_differences` asserts the reported diff
contains only the fields that actually changed, and
`test_compare_runs_finds_no_differences_for_identical_reruns` confirms
two genuinely identical reruns report an empty diff, not a false
positive on `run_id`.

**Verified against the live DB, not just tests.** All 3 scripts were
re-run for real; `list_runs()` against the actual database shows
multiple real runs of `classify.py`, and comparing two of them via
`compare_runs()` shows an empty `differences` dict for every
business-relevant field — real evidence the classifier is reproducible,
not just an assertion in a test.

### M15 — Pipeline Orchestration

**10 requested steps map to 8 real callables, not 10.** `scripts/ingest.py::run()`
already performs ingestion and normalization in one function call (it
calls `normalize_dataframe` internally); `scripts/resolve_products.py::run()`
already performs entity resolution and Product Master generation in one
call. Splitting either of these into two separate orchestrator-level
calls would mean either (a) reimplementing part of what an existing
`run()` function does, duplicating business logic — explicitly forbidden
by this milestone's own brief — or (b) refactoring those scripts to
expose two separate entry points, which is scope this milestone didn't
ask for and risks the same kind of thing it's trying to prevent (breaking
an already-working script for a cosmetic step count). The orchestrator's
`StageResult.covers` field records which of the 10 named steps each real
stage satisfies, so nothing is silently hidden — it's an honest 8-for-10
mapping, not a shortfall.

**`dashboard_preparation` is a genuine no-op, not faked activity.**
`scripts/build_dashboard_data.py` has been a 0-byte file since it was
created and the dashboard has always read DuckDB directly
(`dashboard/components/data.py`). Writing new logic into that stub to
give this stage something to "do" would be inventing a feature nobody
asked for (rule #8, "do not add unnecessary complexity") just to make a
step list look more populated. The stage exists in the orchestrator (so
`--skip-dashboard` has something to skip, and the summary is honest about
there being 10 named steps), but it does nothing, and says so in its own
docstring.

**On failure, every remaining stage is marked `skipped`, not run.** All 8
stages are sequentially dependent — market calculation reads the products
a failed entity-resolution run wouldn't have produced correctly, etc. —
so "stop dependent stages" (the brief's own words) means stop everything
after the failure point, not attempt a per-stage dependency graph. This
is deliberately the simplest correct behavior (rule #8), not a
placeholder for something fancier later.

**Run tracking reuses M14's `pipeline_runs`/`start_run`/`finish_run`
rather than building new logging infrastructure.** The brief asks for
"logging, error reporting, execution summary" — all three already have a
home. The orchestrator records one `pipeline_stage="full_pipeline"` row
covering the whole run, on top of whichever individual stages
(`classify.py`, `classify_product_types.py`, `resolve_products.py`)
already record their own `classification_runs`/`product_resolution_runs`
rows. No new run-tracking table or module was created.

#### Incident: a real, confirmed bug found by the orchestrator's first actual run

`src/dmie/cleaning/normalize.py::normalize_dataframe` has hardcoded
`"category_id": None` for every listing since the function was first
written (M1-M3) — there has never been a code path anywhere in this
project that set a listing's `category_id` to a real value.
`listings.category_id` had nonetheless been correctly `"denture_base"`
for all 105 rows throughout this entire session, because some earlier,
undocumented one-time action (predating this session's history) had set
it directly — and nothing had re-run `scripts/ingest.py` against the live
database since, so the gap in `normalize_dataframe` stayed invisible.

The very first real run of `scripts/run_pipeline.py` called `ingest.run()`
again as its first stage. `upsert_listings`'s `ON CONFLICT ... DO UPDATE
SET category_id = excluded.category_id` then overwrote every listing's
`category_id` back to `NULL`, because that's what `normalize_dataframe`
had always produced. Every downstream stage that filters
`WHERE category_id = ?` (`classify_product_types.py`, `market/aggregation.py`,
`detect_opportunities.py`) silently found 0 matching rows for the rest of
that run — no exception was raised anywhere, the pipeline reported
"success," and the summary just showed 0 relevant listings and 0 products.

This is exactly why real end-to-end runs matter more than unit tests
here: no existing test exercised `ingest.py` twice in a row against
data that already had a real `category_id` set, so nothing caught this
until the orchestrator's own real invocation did.

**Fix:** `normalize_dataframe()` gained a `category_id: str | None = None`
parameter (defaulting to `None` — never a guess — so every existing
caller that doesn't pass one keeps today's behavior exactly), used
instead of the hardcoded literal. `scripts/ingest.py::run()` gained a
matching `category_id` parameter, and `run_pipeline.py` passes the
`--category` value through. **No business definition changed** — this
restores `category_id` to actually reflecting what it always claimed to:
the category a listing was ingested for.

**Verified against the live DB, not just a test:** the corruption was
repaired by re-running the fixed pipeline for real (not a manual SQL
patch) — `listings.category_id` confirmed back to `denture_base` for all
105 rows, and every downstream count (12 relevant, 11 products, 29
opportunity signals with the same type/status breakdown as before)
matched the known-good numbers from immediately after the previous bug
fix. 3 regression tests added:
`tests/unit/test_normalize.py::test_normalize_dataframe_sets_category_id_when_given`
and `..._category_id_defaults_to_none_not_a_guess`, plus
`tests/integration/test_ingest_pipeline.py::test_category_id_survives_a_second_ingest_run`
(runs `upsert_listings` twice in a row against the real denture_base
export and asserts `category_id` is still set on the second pass — the
exact scenario that broke).

### Fix: entity resolution quantity vocabulary (false-merge #3)

Scoped narrowly to the vocabulary gap
`docs/entity_resolution_evaluation_report.md` found (false-merge #3),
not the related but distinct disjointness-logic gap (false-merge #1) —
the user asked specifically for the vocabulary issue. `_QTY_BEFORE_RE`
(`src/dmie/matching/similarity.py::extract_quantities`) recognized
`pcs?|pc|pack|box|ea|piece` but not `bottle`, `set`, `count`, or `ct` —
real words this dataset's titles actually use. `"White 1 Box"` vs
`"White 2 Bottle"` extracted `{"1"}` vs `{}` (empty), and the pack-variant
guard requires *both* sides non-empty, so a real pack-count mismatch
between two same-brand, near-identical-title listings went undetected and
auto-MATCHed at 0.927 confidence.

**Fix:** added `bottle`, `set`, `count`, `ct` to the recognized unit
vocabulary. Deliberately did **not** also change the guard's
full-disjointness requirement to a symmetric-difference check
(recommendation #2 in the evaluation report, which fixes a *different*
false merge — `B0F599K6BR`/`B0F598SL5Q`, where both titles already share
a recognized quantity word "12pcs" that masks a real "1 Piece"/"2 Pack"
difference no vocabulary addition can fix). Vocabulary and disjointness
logic are separate mechanisms with separate risk profiles — bundling them
into one change would make it harder to tell which fix caused which
behavior change if either needed to be revisited.

**Verified against the live DB, not just tests:** re-ran the full
pipeline. The exact real pair from false-merge #3
(`B0GVB7J6PV`/`B0GVB48DSX`) now resolves `UNCERTAIN`/`possible_pack_variant`
instead of `MATCH` — `match_candidates` MATCH count 14 → 13, resolved
products 92 → 93 (one previously-merged pair is now correctly two
products). `product_market_metrics` unchanged at 11 (neither listing is
market-relevant/RELEVANT, so this doesn't touch market-scoped numbers).
5 regression tests added (`tests/unit/test_similarity.py` +4,
`tests/unit/test_resolution.py` +1 using the real ASIN pair). Full suite:
**342 passed**.

### Fix: entity resolution disjointness logic (false-merge #1)

Recommendation #2 from the evaluation report, implemented after the
vocabulary fix above. `resolve_pair`'s pack-variant guard changed from
`q_a.isdisjoint(q_b)` (fires only if the two titles' quantity sets share
*zero* tokens) to `bool(q_a ^ q_b)` (fires if either side has a quantity
token the other doesn't — symmetric difference non-empty). Root cause:
`B0F599K6BR`/`B0F598SL5Q` both contain `"12pcs"` (an unrelated per-kit
component count), so despite also stating a real, different pack size
("1 Piece" vs "2 Pack"), the shared "12" made `isdisjoint()` return
`False` and the guard never fired — the pair auto-MATCHed at 0.911.

**Verified the blast radius before writing any code**, not after:
recomputed `resolve_pair`'s guard condition (old vs. new) for all 91 real
candidate pairs directly against the live DB, comparing decisions before
touching `resolution.py`. Exactly 3 of 91 pairs change:

1. `B0F599K6BR`/`B0F598SL5Q`: `MATCH` → `UNCERTAIN/possible_pack_variant`
   — the intended fix.
2. `B0F9B9LHPW` ("2 Pack (8 Count)") /`B083QN94W5` ("Pack of 2"):
   `MATCH` → `UNCERTAIN/possible_pack_variant` — **a real, legitimate
   match** (both are the same 2-pack Dentemp kit) reclassified as
   needing human confirmation, because one title states an "8 Count"
   sub-detail the other omits. Not a correctness regression — the pair
   was and still is the same product, it's just no longer auto-decided.
   Accepted deliberately: per this project's own established bias
   (`resolve_pair`'s own docstring: "Default policy queues rather than
   rejects"), converting one correct match into a queued item costs a
   quick human glance; the alternative (the bug this fixes) silently
   ships a wrong merge with no human ever looking at it. Not treated as
   a defect to work around — see "what this doesn't fix" below for why
   a more surgical alternative was rejected.
3. `B00VQTLM74`/`B00E4MPAIW`: already `UNCERTAIN` both before and after
   (this is one of the 5 gold-reference pairs in
   `docs/entity_resolution.md`, explicitly documented as a correct
   non-merge) — `match_method` changes from generic `fuzzy_composite` to
   the more accurate `possible_pack_variant`. A labeling improvement on
   an already-correct decision, not a behavior change.

**What this doesn't fix, and why a "smarter" alternative was rejected:**
the real reason case #2 above exists is that `extract_quantities` treats
"count" (items *inside* one retail unit) and "pack" (how many retail
units are being sold) as the same flat concept — splitting them into two
separate axes (so a "count" mismatch alone never triggers the guard,
only a "pack" mismatch does) would fix case #2 without costing anything.
This was considered and **not done**: it requires classifying which
regex alternation matched each number (not just extracting a flat string
set), a real restructuring of `extract_quantities`'s return type and
every caller, to eliminate one already-safe side effect (a correct match
sitting in a review queue) — not proportionate to the problem, and not
what was asked ("fix the disjointness logic issue," not "redesign
quantity extraction"). If the review-queue volume from this class of
case ever becomes a real operational cost, revisit then with real volume
data, not speculatively now.

Regression tests added, using the real ASIN pairs directly:
`tests/unit/test_resolution.py::test_shared_unrelated_number_no_longer_defeats_the_pack_variant_guard`
(case #1) and
`test_consistent_pack_size_with_extra_detail_on_one_side_is_now_queued_not_matched`
(case #2, documenting the accepted tradeoff explicitly so it can't be
"fixed back" unnoticed later). Verified against the live DB: full
pipeline re-run, `match_candidates` MATCH count 13 → 11, resolved
products 93 → 95, `product_market_metrics`/`opportunity_signals`
unchanged (none of the affected listings are market-relevant). Full
suite: **344 passed**.

## Real AI key configuration + a real test-isolation bug it exposed

**`.env` over a permanent shell environment variable.** Offered the
user both (paste the key here and I write it to a gitignored `.env`, or
set it themselves in their own terminal so it never enters this
conversation). They chose the former. Verified `.env` was genuinely
gitignored (`git check-ignore -v`) *before* writing the key to disk,
not after. `python-dotenv` loads it once, at `dmie.ai.client` import
time, with `override=False` so a real deployment/CI environment
variable is never shadowed by a stray local file.

**Tests must not depend on the ambient absence of a real credential.**
This project's entire test suite was written and always ran under one
implicit assumption: no `ANTHROPIC_API_KEY` has ever existed in this
environment, so any unmocked AI code path degrades safely. That
assumption was never encoded as an explicit test fixture — it was just
true, by accident of project history, until this exact change. The
instant it stopped being true, `test_classification_pipeline.py`'s
50-real-call gold-set evaluation crashed the Python process (a native
SSL access violation in httpx2/truststore, not a graceful Python
exception). This is the general risk of implicit test isolation:
correctness that depends on an unstated environmental fact rather than
an explicit guarantee. Fixed by making the guarantee explicit
(`tests/conftest.py`), not by special-casing the one test that happened
to crash first — `test_product_type_pipeline.py`,
`test_resolution_pipeline.py`, and parts of `test_product_type_classifier.py`
had the identical latent gap and are covered by the same fix.

**Session-scoped autouse fixture, not function-scoped — found by
testing the fix, not by reasoning it out in advance.** The first
attempt used a function-scoped `monkeypatch.delenv(...)` autouse
fixture and still didn't prevent the crash. Root cause: pytest sets up
a test's fixtures in scope order (session → module → class → function)
regardless of autouse status, so a module-scoped fixture
(`test_classification_pipeline.py`'s `report`) always initializes
*before* a function-scoped fixture a test also uses, autouse or not.
The real fix had to be session-scoped, which meant it couldn't depend
on pytest's function-scoped `monkeypatch` fixture at all (a
session-scoped fixture cannot depend on a narrower-scoped one) —
switched to instantiating `pytest.MonkeyPatch()` directly. Caught by
actually re-running the full suite after the first fix rather than
assuming a fixture named right and marked `autouse=True` was
sufficient.

**`build_context()`'s median-price gap was found by using the real
feature, not by more code review.** A real question to the real model
("what's the highest-priced product vs. the category median?")
surfaced that `price_distribution`/`sales_distribution` — both already
computed and stored in `category_market_metrics` — weren't in the
context the model was allowed to use. The model's own grounding
instructions correctly caught this (it refused to compute a median
itself rather than fabricating one), which is exactly the behavior
those instructions exist to produce — but it meant a real,
easily-answerable question came back `insufficient_data: True`. Fixed
by including both fields (no new calculation, just a wider `SELECT`),
re-verified with the identical question against the real API.

## Multi-category robustness pass — decisions made under time/API-budget pressure

**Chose not to retroactively repair the ~666/~41-listing cross-category
data loss found live (denture_base 22,801→22,135, dental_models
428→387).** The fix that stops it from happening again going forward
(`upsert_listings()` now rejects and logs a cross-category conflict
instead of silently reassigning) is unconditionally correct and shipped.
Restoring the already-lost rows would require re-ingesting all three
categories' raw files in a deliberately chosen precedence order and
re-verifying counts under more DB access — given the user explicitly
asked to stop spending further time/API budget on this pass, the
honest choice was to ship the forward-looking fix, document the real
current (slightly reduced but internally consistent) counts, and leave
restoration as a clearly-flagged follow-up rather than risk another
long, uncertain operation to chase a cosmetic count.

**Chose not to run real AI relevance classification for
`dental_models`/`implants` to completion in this pass.** Two real
attempts were made; the first hung for 50+ minutes on a single stuck,
untimed network request (a real, now-fixed bug — see PROGRESS.md #5),
and a second, independent attempt (from a concurrently-firing scheduled
background check) produced inconsistent partial results (2/387
`dental_models` listings classified, 0/279 for `implants`) before the
user asked to stop. Rather than immediately re-spending several hundred
more real API calls to "finish the number," the priority shifted to:
find and fix the actual bug (done — client timeout + progress
visibility), verify the fix with tests that don't cost real API calls
(done — full suite passes, all mocked), and report the real, current,
honest state rather than a rushed, possibly-still-flaky full run. This
is a deliberate trade: "the pipeline is now correct and verified" over
"the pipeline has already produced two categories' worth of real
classified data" — the user's explicit budget constraint made this the
right call, not a shortcut taken to save effort.

**Investigated the process-hang root cause via direct measurement, not
speculation, before touching the fix.** When entity resolution appeared
to "hang" for 35+ minutes, the instinct to just add a timeout or kill-
and-retry loop was resisted in favor of first reproducing the slowdown
in isolation (a standalone script measuring `generate_candidate_pairs`
and `resolve_pair` throughput directly against the real data), which
correctly separated two genuinely different problems that looked
identical from the outside: (a) `_variant_policy()`'s redundant
`categories.yaml` file read on every one of 470K pairs (a real
CPU-bound cost, ~264s once fixed), and (b) a completely unrelated
mistake in the *diagnostic script itself* — popping `ANTHROPIC_API_KEY`
from `os.environ` *before* importing `dmie.matching.resolution`, whose
import chain re-loads `.env` via `dotenv.load_dotenv(override=False)`
and silently restored the key, making the measurement script itself
make real (slow) AI calls it wasn't supposed to. Fixing only the first
issue without catching the second would have left the measurement
un-trustworthy; both were confirmed independently before concluding the
`@lru_cache` fix was sufficient.

**Killed two zombie diagnostic processes that ordinary `Stop-Process`
could not terminate.** Twice during this pass, a Python process stuck
in native code (blocked on a hung network call) did not respond to
`Stop-Process -Force`, silently reporting success while the process
remained alive and CPU-idle for minutes afterward — almost certainly
because the process was blocked in a native/kernel-level wait that
doesn't check for the termination signal Windows normally delivers
cooperatively. `Invoke-CimMethod -MethodName Terminate` (WMI's lower-
level termination path) succeeded both times where `Stop-Process`
appeared to but didn't. Recorded here since it's a real, reusable
diagnostic technique for this environment, not a one-off workaround.

## Two real bugs found only by running a second category through the full pipeline, not by inspection

**The AI client timeout fix from earlier in this pass was incomplete,
and the incompleteness cost real API budget before it was caught.**
`timeout=30.0` on `anthropic.Anthropic(...)` was verified working
against ordinary slow responses, but a rarer failure mode -- a stall in
the OS network stack itself, before httpx's own timeout logic ever
starts its clock -- bypassed it entirely, and one listing hung for 2.8
hours before being manually killed. The fix that actually closes this
(a background-thread hard wall-clock watchdog via
`concurrent.futures.ThreadPoolExecutor.result(timeout=...)`) was only
found by watching a real run closely enough to catch the anomaly in the
log, not by reasoning about the SDK's timeout parameter in the abstract.
Lesson applied going forward in this session: a fix that isn't observed
succeeding against real, messy, live conditions (not just a clean happy-
path test) isn't verified yet, no matter how principled it looks on
paper.

**The `replace_products` PRIMARY KEY collision was a direct, foreseeable
consequence of an earlier decision (not retroactively repairing the
cross-category listing corruption) that wasn't fully traced through at
the time.** When PROGRESS.md's earlier entry noted "not retroactively
repaired... the live DB currently reflects this real discovered state,"
the downstream implication -- that a stale `products` row from an
earlier, unrelated pipeline run could still be rooted on a listing_id
that has since changed category, and that `product_id` is a global
primary key oblivious to category -- wasn't worked through until it
actually broke a real run. Fixed properly (delete any colliding
product_id regardless of category, not just a category-scoped delete)
rather than working around it (e.g. catching the exception and skip-
logging it, which would have silently dropped a real product from the
Product Master). Recorded so future category onboarding knows to expect
this class of issue rather than being surprised by it again.
