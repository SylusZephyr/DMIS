DMIS · Dental Market Intelligence OS

Everything you need to present DMIS and answer any question about it

Read top to bottom once (about 35 minutes), then spend the rest of your hour on the question drill at the end. Green quotes are lines you can say out loud. Amber boxes are demo tips.

The 60-second pitch

Say thisDMIS turns SellerSprite exports of Amazon US listings into a statistical picture of a product category: how big the market really is, who controls it, where the demand gaps are, whether it is growing, and which product we should launch. Every number carries a 95% confidence interval and its formula. The tool has been validated against markets where we know the true answer, and it works in English and Chinese.

Three things make it different from a normal sales dashboard:

  • It corrects the data's blind spot. Amazon only shows sales badges like "200+ bought in past month". Adding those up undercounts the market by about a third. DMIS models the real sales behind each badge.
  • It never pretends to be certain. Every estimate has an interval, and every "significant" claim has passed a statistical test with false-discovery control.
  • It is universal. Nothing is hard-coded for dental data. Category rules live in config files, and the maths works on any category's export.

The problem and the big idea

What the input looks like

The input is a SellerSprite export (Excel or CSV) of Amazon US listings. It has title, brand, price, rating, reviews, launch date, category, and a sales column that is usually a badge ("50+", "100+", "200+ bought"). The raw files live in data/raw/ and are never modified: they are the evidence.

Three core principles (from PRINCIPLES.md)

Listing ≠ Product

One product can be sold through many ASINs (colours, bundles, sellers). DMIS groups listings into products and never counts listings as product types.

Code calculates, AI interprets

Python and DuckDB do all the maths. AI is used only for meaning: relevance, classification and phrasing. It never produces a number.

Never silently discard

Every excluded listing keeps a reason ("rejected: …", "not relevant: …", "low data quality: …"), visible on Data Operations.

The badge problem, in one picture

A badge is a range, not a number. "200+" means 200 to 299 on a ladder of 50, 100, 200, 300 … 900, 1K, 2K … 5K, 10K … A listing with no badge sells below 50, not zero. Summing the badge floors gives a certain lower bound (the "floor"). On synthetic markets that floor is about 34% below the truth. DMIS treats each listing as an interval-censored observation and estimates where inside the interval its true sales most likely are.

Say thisOther tools add up the badges and report the floor. We treat each badge as a range, fit a demand model to all listings at once, and estimate the real total. On test markets with known truth we're within about 2%, against 34% for the badge sum.

Under the hood: how the pieces connect

The path of one click

  1. The browser loads a page from Next.js on port 3000. Each page is a React client component ("use client").
  2. The page calls useApi("/markets/…") (frontend/lib/hooks), which does fetch("/api/v2/…") with an optional Authorization: Bearer token from localStorage (frontend/lib/api.ts).
  3. Next.js rewrites /api/v2/* to the FastAPI server (default http://127.0.0.1:8000, overridable with DIP_API_URL) in next.config.ts. Browser and API share one origin, so no CORS is needed.
  4. FastAPI (src/dip/api/app.py plus routes/*.py) checks the role and market scope (auth.py: require("markets","read"), assert_market), then reads data.
  5. Market tables are read from Parquet via DuckDB (lake.read_curated(table, market)). Business records are read with SQLAlchemy sessions (business.session()).
  6. Read endpoints are memoised by @response_cache per (arguments, data version, market scope), so repeat views are instant and a new upload invalidates them.
  7. The JSON goes back to the page, which draws it with ECharts or three.js.

Jobs, auth and caching

  • Upload processing: by default a background thread in the API. With DIP_JOB_MODE=queue, the API writes to job_queue and a separate dmis.py worker processes jobs, which suits production. Stage progress is written to jobs and polled by the UI.
  • Auth: Authorization: Bearer dmis_… tokens. Only the SHA-256 hash is stored. Tokens expire after 90 days, and permissions are checked per role, resource and action. DIP_AUTH=off runs as a local admin for laptop use.
  • Audit: middleware records every POST, PUT, PATCH or DELETE (user, route, status). Read-only computations such as simulations and questions are excluded.
  • Galaxy layout: segment centres are placed around a sphere. Inside a segment, products are spread by the first 3 SVD components of their title embeddings, and the coordinates (gx, gy, gz) are stored on products.

The statistics, explained plainly

Every formula has an ID (M1.1, M2.1 …) that links to docs/METHODOLOGY.md and the in-app Methodology page. These are the ones you must be able to explain.

1 · Badge detection (M1.1, observation.py)

If at least 98% of observed sales values sit exactly on the ladder (50, 100, 200 …), the column is treated as badges. Otherwise the values are treated as exact sales. The decision comes from the data itself.

2 · The demand model (M1.2, demand.py)

log(units) = b0 + b·z + σ·ε z = standardised log price, rating, log age, sub-category ε ~ Normal, or Student-t (df 10, 5, 3) for heavy tails, chosen by AIC

The model is fitted by maximum likelihood on intervals: a listing with "200+" contributes the probability that its sales fall in [200, 300), and a listing with no badge contributes P(sales < 50). This is called interval-censored regression. A small ridge penalty keeps it stable. With few badged listings it falls back to an intercept-only model.

Bootstrap (60 refits, parametric) captures parameter uncertainty and corrects small-sample bias. Each refit also re-chooses the error family.

3 · Listing estimate (M1.3)

For each listing: the expected sales given its badge range (the conditional mean), plus a 95% interval. The estimate always stays inside the observed range.

4 · Market, segment, brand and product totals (M1.4)

400 joint simulations draw every listing at once and sum by group. The interval comes from those draws, widened by interval_inflation = 1.3, a factor calibrated on synthetic markets so that 95% intervals really cover 95%. The point estimate is the sum of the listing estimates, and the draws are rescaled to it. As a result, every level adds up exactly: listings, products, brands, segments and the market.

The market card shows three numbers: the floor (certain lower bound), the estimate with its 95% interval, and the ceiling (the sum of upper bounds, when all listings are bounded).

5 · Concentration: HHI (M2.1)

HHI = Σ (brand share × 100)² range 0–10,000 · above 2,500 = highly concentrated effective competitors = 10,000 / HHI

Shares come from the simulation, so HHI has an interval too. P(#1) is the fraction of simulations in which a brand ranks first. A brand is a "leader" when P(#1) ≥ 50%. It is "above par" or "below par" only when its whole interval sits above or below the equal-share benchmark (1 ÷ effective competitors).

6 · Entry: entrant success rate (M3.x)

An entrant is a listing launched in the last 365 days. Success means reaching the median sales of established listings. Segments with fewer than 5 entrants are shrunk toward the market rate (empirical Bayes, prior strength 5), so one lucky listing can't make a segment look easy.

7 · Unit economics (M4)

unit margin = price × (1 − referral fee 15%) − fulfilment fee − unit cost

A cost column that is almost a fixed percentage of price is detected as derived from price and never used as a real cost. Without genuine costs, profit is not shown.

8 · Quality gap (M5)

The share of demand going to listings rated below 4.0. It is a customer-pain proxy used when there is no review text. The rating bar is the median rating of the top 10% of listings by revenue.

9 · Opportunity index 0–100 (M7)

A weighted geometric mean of six components, each mapped to 0–1 on an absolute scale so markets are comparable:

ComponentWeightScale (0 → 1)
Demand0.25segment revenue, log scale: $1k → 0, $1M/month → 1
Entry0.25entrant success 0% → 0, 60% → 1
Margin0.20median margin 0% → 0, 40% → 1
Competition0.15HHI 5,000 → 0, 1,000 → 1
Quality gap0.10upside only: no gap = neutral 0.5, 40% gap → 1
Saturation0.0595% "dead" listings → 0, 50% → 1

Why geometric? A zero in one component (for example, impossible entry) drags the whole index down. An arithmetic average would hide that. Missing components are left out and the coverage is shown. A product index = 0.7 × its segment + 0.2 × its price-band position + 0.1 × its quality room (also geometric).

10 · Evidence grade A–D

A: ≥ 50 listings, ≥ 25% badged, hold-out AUC ≥ 0.75. B: ≥ 20, ≥ 10%, AUC ≥ 0.65. C: ≥ 10, ≥ 5% badged. Otherwise D. The AUC comes from 5-fold cross-validation: can the model tell which listings earned a badge without seeing their badge? 0.5 is chance.

11 · Demand gaps and the recommended product (M10)

For every segment with ≥ 8 listings, every candidate feature (a title term like "teaching", a bucketed spec like "rpm 40k–60k", or a price band) gets a lift: demand per listing with the feature ÷ without it, with a bootstrap interval (400 resamples). The p-values are corrected with Benjamini–Hochberg (false discovery rate 10%). A feature is a gap when it is significant and under-supplied. The recommended product combines up to 3 co-occurring gap features with the best price band. If no gap is significant, it recommends the best price band only.

12 · Significance for alerts (M8, significance.py)

z = (log after − log before) / √(se_before² + se_after²), se from each 95% interval

All changes in one run are BH-adjusted. Only q ≤ 0.05 becomes an alert. Changes that are not significant stay in the log as "info". With exact data (no uncertainty), any change is certain.

13 · Growth and forecast (M15, forecast.py)

This needs ≥ 3 dated monthly snapshots. It fits a random-effects log-linear trend: each snapshot is weighted by its own uncertainty plus real month-to-month variation τ², estimated by the method of moments (DerSimonian–Laird). Outputs:

  • growth per month with a t interval, and a p-value for "trend = 0"
  • direction: growing, declining, or no significant trend
  • 3, 6 and 12-month forecasts with 95% prediction intervals; ⚠ marks a horizon longer than the history

Seasonality is not modelled until 24 monthly snapshots exist. Validation: the intervals covered the truth 96–100% of the time on simulated series.

14 · Launch simulator (M12, metrics/launch.py)

The fitted demand model is stored as a model card. For a new idea (title, price, optional cost), DMIS places it in the closest segment by text similarity and draws posterior-predictive sales for a new listing. It then outputs:

  • units, revenue and profit as distributions: median, p10–p90, P(profit > 0), P(reaching the target)
  • break-even and payback
  • a price curve
  • the gaps the idea covers and the risks it runs
  • what real entrants in that segment actually sell

Scenarios use common random numbers, so differences between prices come from the price, not from noise. The price effect is a cross-sectional association, not a causal elasticity, and the UI says so.

15 · Shopping mode (M13)

For buyers. Products are compared on four criteria: requirement match, Bayesian rating (a rating shrunk toward the market mean by review count), proven demand (the lower bound of sales) and price. The Pareto front is the set of products no other product beats on every criterion. A dominated product names the product that beats it.

16 · Knowledge graph (M14)

Every edge has evidence, a basis (fact, estimate, test or similarity) and a strength (0–1). Path finding uses weight 1 + (1 − strength), so among equally short paths the best-evidenced one wins. Edges that are not significant are never drawn.

17 · Inside a sub-category and product position (M16)

Top brands with share intervals and P(#1), demand per listing by price band (bootstrap, 2,000 resamples, fixed seed), and launch momentum (an exact binomial test: launches in the last year vs the year before). A product's percentile is the share of peers below it, with ties counted half.

18 · Opportunity Board (M17, board.py)

For each market's top 8 sub-categories by opportunity index, the board shows the gaps engine's concept, priced at the geometric middle of its range. When the segment is too small, it uses the typical product at the median price and says so. Each concept is simulated with the launch simulator and joined with growth, the leading brand and entry. Nothing is re-scored.

Say this if asked "why so much statistics?"Because a sales dashboard that shows one number invites overconfidence. A launch decision needs to know the range of outcomes and whether a difference is real or noise. Every technique here answers one of those two questions.

Configuration: "no hard-coding"

This is the answer to "does it only work for dental?". No. Everything category-specific or tunable is in YAML:

  • config/categories.yaml: what belongs in a category (include and exclude terms, sub-categories). A new category needs a new entry here, not code.
  • config/platform/metrics.yaml: the badge ladder, error families, bootstrap and simulation counts, interval inflation 1.3, entrant window 365 days, referral fee 15%, opportunity weights and scales, evidence grades, gap settings (FDR 10%), alert FDR 5%, forecast (min 3 periods), board size (8).
  • config/platform/analyst.yaml: Gemini model, number tolerance, top-N.
  • plans.yaml (tenancy limits, token lifetime 90 days), confidence.yaml, sourcing.yaml (supplier scoring weights).
  • Secrets live in .env, which is never committed: GEMINI_API_KEY, DIP_POSTGRES_URL, DIP_NEO4J_URI, DIP_QDRANT_URL, DIP_AUTH.

How accuracy is proven

  • Synthetic ground truth (metrics/synthetic.py): generate markets with known true sales (sub-categories, price elasticity −0.9, rating and age effects, normal or heavy-tailed noise, missing data), apply the real badge censoring, and check whether the model recovers the truth. Calibration markets and validation markets are different seeds.
  • Hold-out AUC on real data: hide badges and predict them. Per market pass/watch/fail (target 0.70).
  • Human labels: the precision and recall of relevance and grouping come only from people labelling samples.
  • Launch calibration: launched projects' actual sales against their predicted p10–p90.
  • Invariant tests: totals add up at every level; shares sum to 1; every estimate lies inside its interval.
  • Acceptance test (test_acceptance_v3.py): a full bilingual user journey: two uploads, size, segments, competitors, launch, shopping, graph path, analyst EN and ZH, alerts, project, opportunity board, accuracy.

Traceability of AI

Every AI call is stored in ai_traces: model, prompt version, input hash, output, status and timestamp, as PRINCIPLES.md principle 6 requires. Analyst replies containing any number not in the computed facts are rejected, and the computed answer is shown instead.

Limitations and roadmap (say these confidently)

  • Growth needs time: at least 3 dated monthly exports for a trend, 24 for seasonality. The current data are single snapshots, so growth pages say "needs snapshots" rather than inventing a trend.
  • No review text in the current exports. Customer pain uses the rating-based quality gap until reviews are uploaded.
  • No supplier list has been supplied yet, so supplier matching is empty.
  • Price effect is associational, not causal: listings at different prices differ in other ways too.
  • Human labelling (about 50 products per market) is still needed to report real precision and recall.
  • Operations gaps: no billing provider; one organisation per user; the Amazon SP-API connector is not wired.
  • Next steps: monthly exports, labelling, a backtest on history, a 4-week pilot with 3–5 users, then an exit report.

Basics (expect these first)
What is the tech stack?

Backend: Python with FastAPI. Data: Parquet files queried with DuckDB, plus SQLite by default or PostgreSQL through SQLAlchemy. Graph: NetworkX or Neo4j. Vectors: Qdrant. Ingestion: Polars. Statistics: NumPy, SciPy, scikit-learn, XGBoost. Frontend: Next.js 16, React 19, TypeScript, Tailwind, ECharts, three.js. AI: optional Google Gemini. Deployment: Docker.

How is the database connected?

Through SQLAlchemy. settings.business_url is DIP_POSTGRES_URL if set, otherwise sqlite:///data/platform/business.db. create_engine is cached per URL; on first connect it creates tables, runs an additive migration and seeds permissions. Code opens with business.session() as s. Analytical tables are Parquet files read by DuckDB with read_parquet, so there is no database server.

How does the frontend talk to the backend?

The pages call fetch('/api/v2/…'). Next.js rewrites that path to FastAPI on port 8000 (next.config.ts, DIP_API_URL), so everything is same-origin with no CORS. Responses are JSON, and a bearer token is added when auth is on.

Why FastAPI? Why Next.js?

FastAPI: Python is where the statistics live; it gives typed request validation (Pydantic), automatic API docs at /docs and good performance. Next.js with React: file-based routing (one folder per page), server rewrites to proxy the API, and the React ecosystem for 3D (react-three-fiber) and charts.

Why DuckDB and Parquet instead of putting everything in Postgres?

Market data is analytical: wide, columnar and read-heavy. Parquet is compressed and columnar, and DuckDB runs fast SQL straight on the files with no server. Operational records (users, projects, alerts) need transactions, so they go in SQL. This is a standard lakehouse split.

Does it need the internet?

No. Everything runs offline on a laptop, including embeddings, which are hash-based rather than an external model. Only the optional Gemini phrasing and the optional live connectors need the network.

What data does it take in?

SellerSprite exports in Excel, CSV or JSON. Columns are detected automatically (Chinese headers too). Optional extras: a snapshot date, a reviews file (id, text, rating), and a supplier list (CSV template in data/templates).

How many pages and how many API endpoints?

About 25 pages in the sidebar plus product and market detail pages. The API has about 120 endpoints under /api/v2, across metrics, catalog, intelligence, enterprise, workflow, operations, people, pilot, orgs, auth. The full list is at localhost:8000/docs.

Where is the data stored on disk?

data/raw holds the untouched inputs. data/lake/curated/<table>/market=<name>/data.parquet holds the market tables. data/platform/ holds business.db, graph.duckdb, the vector store and the accuracy run results. Generated data is not committed to git.

How is the project organised in git?

The work was done on feature branches, one pull request per phase (PR #2 to #7), each merged to main after green CI. GitHub Actions runs the Python tests and the frontend lint, type-check, build and i18n check.

Infrastructure & engineering (intermediate)
How are uploads processed without blocking the UI?

The upload returns a job_id immediately. Processing runs in a background thread, or with DIP_JOB_MODE=queue in a separate worker process that reads job_queue. Each stage writes its status, seconds and peak memory to jobs, and the UI polls /jobs/{id}.

How do you avoid stale or slow reads?

@response_cache keys each read by its arguments, the data version and the user's market scope. Processing a market bumps the version, so caches invalidate automatically. The Opportunity Board caches per market run (run_id:updated_at).

How is security handled?

Bearer tokens; only the SHA-256 hash is stored; 90-day expiry; revocation. There is role-based access control (7 roles), market-scoped product managers, and multi-tenant organisations with plan limits. An audit log records every state change. Secrets live in .env, which is never committed.

How do schema changes work without losing data?

business.migrate() compares the models with the live tables and ALTER TABLE … ADD COLUMNs any missing nullable column. It never drops anything. The lake is rewritten per market on each run.

How does it scale to a million rows?

Polars streaming ingestion and vectorised NumPy stages; records are joined by id without copying. The bootstrap is capped at 20,000 rows and cross-validation at 5,000 (fixed-seed subsets); simulations use bincount group sums. The galaxy draws the top 3,000 products by revenue and states the share drawn.

How are backups done?

python scripts/dmis.py backup writes an archive of the business DB, lake and settings; restore ARCHIVE restores it. In embedded mode the archive holds everything in the platform and lake folders (SQLite, DuckDB, embedded graph, local Qdrant). With servers, PostgreSQL is dumped, while Neo4j and Qdrant servers are rebuilt by re-processing or backed up with their own tools.

How are the similarity embeddings made, and why not a big AI model?

A hashing vectoriser over words (1–2-grams) and characters (3–5-grams), randomly projected to 256 dimensions and normalised. It is deterministic, offline, instant and good at near-duplicate product titles. The design notes that swapping in a sentence-embedding model only means replacing embed().

How is the galaxy layout computed?

Segment centres are spread around a sphere. Within a segment, products are placed by the top 3 SVD components of their title vectors, so similar titles sit close together. The coordinates are stored as gx, gy, gz during processing.

How is translation done?

Every UI string is a key in messages/en.ts and zh.ts, read through useI18n().t(key, vars). The language is stored in localStorage (dmis_lang). Backend sentences that are generated (formula bases) are translated by pattern rules in basis-zh.ts, and anything unmatched is shown in English rather than guessed. Segment descriptions are generated in both languages. check-i18n.mjs fails CI on missing keys or hard-coded English.

Concept
What problem does DMIS solve in one sentence?

It tells a product team, with measured confidence, how big an Amazon category really is, who controls it, where unmet demand is, and which product to launch, from exports that only show vague sales badges.

Why can't you just add up the sales numbers?

They are badges ("200+"), not numbers. A badge is a range, and unbadged listings still sell (fewer than 50). Summing the floors undercounts by about 34%. We model the true value inside each range.

What's the difference between a listing and a product?

A listing is one ASIN. A product is the underlying item and may have several listings (colours, packs, sellers). DMIS resolves listings into products and never counts listings as product types.

Is this tool only for dental products?

No. Category rules live in config/categories.yaml and every statistical setting in metrics.yaml. The dental exports were used for learning and reference only. Badge detection, segmentation and all maths run on any category.

Where is AI used, and where is it not?

Used for semantic judgement: relevance, classification, and optional phrasing of analyst answers (Gemini). Never used for numbers: all aggregation is Python/DuckDB. The Gemini reply is rejected if it contains any number not in the computed facts, and every AI call is logged with model, prompt version, input, output and status.

Statistics
How is market size calculated?

An interval-censored log-linear demand model (price, rating, age, sub-category; normal or t errors chosen by AIC) is fitted to all listings. Each listing gets its expected sales given its badge range. The market estimate is the sum of those. 400 joint simulations with bootstrap parameters give the 95% interval, widened by the calibrated factor 1.3.

How do you know the 95% interval is really 95%?

We generated synthetic markets with known true sales, applied the real badge censoring, and counted how often the interval contained the truth. The widening factor 1.3 was calibrated on one set of markets and verified on different ones. The latest run: 100% market coverage, 1.7% median error.

Why is there a floor and an estimate?

The floor is certain (every listing at the bottom of its badge), but it is biased low. The estimate is our best value with an interval. We show both so nobody confuses the two.

How is the opportunity index built, and why geometric mean?

Six components (demand 25%, entry 25%, margin 20%, competition 15%, quality gap 10%, saturation 5%), each on an absolute 0–1 scale. A weighted geometric mean means one fatal weakness pulls the score down instead of being averaged away. Missing components are left out and coverage is shown.

What does "significant" mean in this tool?

A formal test (bootstrap intervals for gaps, a z-test on log estimates for changes, exact binomial for launch momentum, a t-test for trend) with Benjamini–Hochberg false-discovery control when many things are tested at once. Non-significant results are shown as "within noise" and never raised as alerts.

What is HHI and what does 2,432 mean?

The sum of squared brand shares (in %). Above 2,500 is highly concentrated. 2,432 is moderately concentrated, equivalent to about 4.1 equal-sized competitors (10,000 ÷ HHI).

What is P(#1)?

The share of the 400 simulations in which a brand has the highest revenue. It tells you whether a "leader" is really ahead or just ahead by noise. At 50% or more we call it a leader.

How does the recommended product get chosen?

In each segment with at least 8 listings, every candidate feature's demand lift is estimated with a bootstrap interval. The p-values are BH-corrected at 10% FDR, and significant, under-supplied features are gaps. Up to 3 co-occurring gaps are combined with the best price band. If no gap is significant, it says so and recommends the best price band.

How does the forecast work, and why does it say "needs snapshots"?

A random-effects log-linear trend across monthly snapshots, each weighted by its own interval plus estimated month-to-month variation. It needs at least 3 dated snapshots; we currently have one per market, so it refuses to invent a trend. Forecasts beyond the observed history are flagged ⚠, and seasonality needs 24 months.

Is the price effect causal? Can I set prices with it?

No, it is a cross-sectional association (cheaper listings may differ in other ways). The simulator says so. Use it to compare scenarios, and confirm with real tests.

What is the evidence grade?

A–D, based on the number of listings, the share with a badge, and the hold-out AUC. A needs ≥ 50 listings, ≥ 25% badged and AUC ≥ 0.75. At C or D, trust the intervals, not the point estimates.

Do the numbers add up across pages?

Exactly. Listings sum to products, products to brands and segments, segments to the market. Each total is the sum of its listings' expected sales, and simulation draws are rescaled to it. An automated invariant test enforces this. Segment and brand shares sum to exactly 1.

Deep statistics (expert follow-ups)
Write the likelihood of the demand model.

For listing i with log-mean μᵢ = xᵢβ and scale σ: an exact observation contributes the density f((log yᵢ − μᵢ)/σ)/σ. A badge interval [L, U) contributes F((log U − μᵢ)/σ) − F((log L − μᵢ)/σ). No badge contributes F((log 50 − μᵢ)/σ). F is the normal or Student-t CDF. We maximise the sum of the logs, minus a ridge penalty on the standardised coefficients.

How do you choose between normal and heavy-tailed errors?

We fit normal, t10, t5 and t3 and pick by AIC. With fewer than 30 badged listings only normal is allowed, because the tail shape isn't identifiable. Each bootstrap refit re-selects the family, so model uncertainty is carried into the intervals.

What is the bias correction?

Censored MLE is biased in small samples. We estimate the bias with the parametric bootstrap (mean of refits minus the original fit) and subtract it: β̂_bc = 2β̂ − mean(β̂*).

Why parametric rather than case bootstrap?

Both were tested on synthetic markets; the parametric bootstrap gave calibrated coverage. That is recorded as bootstrap_method: parametric in the config.

How is a listing's conditional mean computed?

E[Y | L ≤ Y < U]. For normal errors in log space there is a closed form: exp(μ + σ²/2)·[Φ(b − σ) − Φ(a − σ)] / [Φ(b) − Φ(a)], with a and b the standardised bounds. For t errors we use 64-node midpoint quadrature over conditional quantiles. The result is clipped into [L, U), and exact observations keep their value.

Why multiply the interval width by 1.3? Isn't that a fudge?

It is a calibration, not a fudge. Raw simulation intervals under-covered on synthetic truth (misspecification and finite-sample effects). The factor needed for 95% coverage was 1.29 on normal markets and 1.30 on heavy-tailed ones, calibrated on 80 markets and verified on 80 different ones. The method is documented in METHODOLOGY §1.4–1.5.

Point estimate: simulation mean or sum of listing means? Why?

The sum of the listings' conditional means. It is deterministic and additive, so every level of the hierarchy reconciles. On 24 synthetic markets it was as accurate as the draw mean (2.0% vs 1.9% median error, both unbiased). Each group's simulation draws are rescaled to that sum, keeping intervals, shares and ranks consistent. Without this, clipping small groups at 0 had inflated product totals (for example $179.5k of products under a $175.8k market).

How do shares sum to exactly 1 with rescaled draws?

Shares are computed per simulation as a member's draw divided by the sum of all members' draws in that simulation (segments of the market, brands of a segment), then averaged. This is self-normalising, so they sum to 1 in every draw.

Explain Benjamini–Hochberg and why FDR instead of Bonferroni.

Sort the m p-values; q₍ᵢ₎ = min over j ≥ i of p₍ⱼ₎·m/j. Rejecting all q ≤ α controls the expected share of false discoveries at α. Bonferroni controls the chance of any false positive, which is far too strict when we test hundreds of features and would hide real gaps.

How is the lift interval computed for a demand gap?

400 bootstrap resamples of the segment's listings. In each, lift = mean units with the feature ÷ mean units without it. The percentile interval and a bootstrap p-value (share of resamples with lift ≤ 1) follow. Features need at least 5 listings with and 5 without.

How is entrant success shrunk?

Empirical Bayes: segment rate = (successes + k·market rate) / (entrants + k), with k = 5 pseudo-entrants. Segments with many entrants keep their own rate; small ones move toward the market rate.

Describe the forecast model precisely.

log yᵢ = a + b·tᵢ + uᵢ + eᵢ, where eᵢ ~ N(0, sᵢ²) comes from each snapshot's interval (sᵢ = (log hi − log lo)/(2·1.96), floored at 0.01) and uᵢ ~ N(0, τ²). τ² is estimated by method of moments (DerSimonian–Laird generalised to regression, floored at 0). a and b are fitted by weighted least squares with weights 1/(sᵢ² + τ²). Growth = e^b − 1 with a t interval on n − 2 degrees of freedom. The h-month forecast variance is var(a + b·t) + τ². Time is measured as days / 30.4375.

What is the significance test for a change between snapshots?

On the log scale: z = (log after − log before)/√(se₁² + se₂²), with each se from its 95% interval, and a two-sided normal p-value. All tests in one run are BH-adjusted and q ≤ 0.05 is significant. Log scale is used because revenues and shares are positive with asymmetric intervals.

How does the launch simulator produce a distribution for a product that doesn't exist yet?

It uses the stored model card (coefficients, bootstrap sets, error family, covariate standardisation). The idea is placed in the nearest segment by text similarity, and a segment offset (the segment's mean residual, shrunk) is added. Covariates: the given price, rating (default: the segment median, stated), and age. Then 400 draws come from the posterior predictive (a parameter set, then noise from the error family), truncated at the top-rung cap so heavy tails don't give infinite means. Profit = units × unit margin − fixed costs.

Why "common random numbers" in scenario comparison?

The same random draws are used for every scenario, so the difference between two prices reflects the price, not sampling noise. This is a variance-reduction technique, and it also makes the price curve smooth (shared_noise).

How is the evidence grade's AUC computed?

5-fold cross-validation on real data: fit on 4 folds with their badges, predict the held-out listings' probability of being above the first rung, and compute ROC-AUC against which ones actually carried a badge.

How is the Bayesian rating computed?

(v·R + C·m)/(v + C), where R is the product's rating, v its review count and m the market mean. The prior strength C is data-driven: the median review count of rated listings. With no review counts in the source, each listing counts once, and that basis is stated.

How does the Pareto ranking work?

Product A dominates B if A is at least as good on every criterion (match, Bayesian rating, proven demand, price) and strictly better on one. Fronts are peeled repeatedly: front 1 is undominated, front 2 is undominated once front 1 is removed, and so on. Within a front, products are ordered by the buyer's weighted utility. A dominated product is never ranked above its dominator, and a test checks this.

How are product percentiles computed?

Mid-rank: (number of peers strictly below + 0.5 × number tied) ÷ number of peers, per metric, within the product's segment.

How is the price-band demand interval computed?

Price bands are within-segment price quantiles (4 bands). There are 2,000 bootstrap resamples over listings with a fixed seed. The interval covers the band's mean units per listing and its share of segment revenue, so it measures sampling variation. Each listing's own model interval is separate.

Challenge questions (skeptics)
"Your estimate is just a model. Why trust it over the real badge numbers?"

The badge sum is also a number, and it is provably about 34% too low. We don't replace the badges: every estimate stays inside its listing's badge range, and we still show the certain floor. We measured the model on markets where the truth is known and reported the error and coverage.

"Synthetic data isn't real data. How do you know it works on real markets?"

Synthetic truth is the only way to measure bias exactly, and it uses the real badge censoring. For real data we add per-market hold-out AUC (badges hidden, then predicted), human labelling for precision and recall, and a launch-calibration check once projects launch. The evidence grade drops when real-data validation is weak (denture_base AUC 0.46 is shown as a fail).

"The interval is huge. Isn't that useless?"

A wide interval is information: the data can't pin the number down. It tells you to collect more (monthly snapshots, exact sales) before betting. A tool that shows one confident number in that situation is hiding the risk.

"Why are opportunity weights 25/25/20/15/10/5? Isn't that arbitrary?"

They are explicit, documented and configurable in metrics.yaml, not hidden in code. Each component is on an absolute, interpretable scale, and the page shows every component so you can disagree with one piece. The alternative, an opaque learned score, would need launch-outcome labels we don't have yet. Launch calibration will let us revisit the weights.

"Couldn't the AI just make up numbers?"

No. The analyst's answer is a list of facts computed by code, each with a verify link. The optional Gemini step only rephrases them. A number guard extracts every number in the reply (handling %, k, M and 万) and rejects the reply if any is not in the facts within tolerance. Every call is traced.

"What if the category boundary is wrong, e.g. water flossers in implants?"

Relevance rules are in categories.yaml. On the Market page you can confirm or override each sub-category's inclusion, and it applies on the next run. Excluded listings are never deleted; they keep a reason. We found exactly this: about 96% of the "implants" export is water flossers, so only $12.7k/month is in scope, grade D.

"What's the single biggest weakness?"

Time-series depth. With one snapshot per market we can size, segment and compare, but we can't prove growth. The system says so instead of guessing. Three or more monthly exports unlock the growth and forecast features.

"How long does processing take?"

For the provided exports (a few hundred listings each), roughly a minute per market, including the bootstrap and 400 simulations; the exact time depends on the machine. Stage timings are shown live on Data Operations, and the pipeline is built to scale to 10⁶ rows.

Each change between snapshots is tested against both snapshots' intervals, with BH correction across the run. Only significant ones (q ≤ 0.05) reach owners; the rest stay as "info" in the log.
